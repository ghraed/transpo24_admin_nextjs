# Transpo24 Admin

Run commands from `admin/`, the Next.js application and Git repository root. Use Node 22 (`nvm use`) and the pinned pnpm version (`corepack enable`, then `pnpm install --frozen-lockfile`).

## Structure

- `src/app/(auth)`: login, registration, and password reset pages.
- `src/app/(protected)`: a shared server session check and client session boundary; existing URLs are preserved.
- `src/app/(protected)/(dashboard)`: the shared navigation layout and operational routes.
- `src/features`: domain-specific screens, API adapters, types, and, for the larger screens, hooks and presentation components.
- `src/lib/api`: HTTP client, error normalization, and the common Refine adapter.
- `src/lib/auth`: session validation shared by the server and browser, with regression tests.
- `src/components`: shared UI and layout components.

Account deletion remains public. Proof images require an admin session but use their own full-screen presentation.

## Authentication

Session checks call the existing guarded `GET /admin/users/:id` endpoint with the bearer token. The token subject is decoded only to locate the account; the backend validates its signature, expiry, active state, and admin role. Both legacy signed tokens and JWTs are supported. Identity and permissions come from the API, not the `auth` cookie. Backend failures remain retryable errors. The API URL must be reachable from both the Next.js server and the browser.

The existing direct-to-API bearer-token model is retained: the browser-readable token cookie is required by API and web-push requests. It uses SameSite=Lax and Secure on HTTPS. Migrating to an HttpOnly session would also require moving authenticated browser API calls behind a server proxy.


## Environment

Required frontend environment variables:

```env
NEXT_PUBLIC_API_URL=http://localhost:3001
NEXT_PUBLIC_SOCKET_URL=http://localhost:3001
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=replace_with_your_google_maps_api_key
NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC_KEY=
```

Only the public VAPID key belongs in Next.js. Never place the VAPID private key in this project.

## Browser Web Push

This admin app now supports browser Web Push for authenticated admin users.

- Service worker: `public/sw.js`
- Subscription endpoints used:
  - `POST /notifications/web-push/subscriptions`
  - `DELETE /notifications/web-push/subscriptions`
  - `GET /notifications/web-push/subscriptions/me` is supported by the backend but not required by the current UI flow

Behavior:

- The service worker is registered in the browser only.
- Notification permission is requested only after the user clicks the enable button in the dashboard.
- If permission is already `granted`, the app synchronizes the existing browser subscription after authenticated startup.
- During logout, the app removes the backend association and unsubscribes locally so the next admin on the same browser does not inherit the previous subscription.

Permission states:

- `default`: the app shows an enable action and does not open the browser permission dialog automatically
- `denied`: the app explains that permission must be re-enabled from browser site settings
- `granted`: the app reuses or creates the browser subscription and synchronizes it with the backend

## Local Testing

1. Set `NEXT_PUBLIC_WEB_PUSH_VAPID_PUBLIC_KEY` to the public key generated by the NestJS backend.
2. Start the backend and this admin app.
3. Open the dashboard on `localhost`.
4. Click `Enable notifications` from the dashboard card.
5. Confirm the browser permission prompt.
6. Trigger an admin Web Push event from the backend.

`localhost` is a secure context for development. Plain LAN HTTP addresses may not support all service-worker and browser notification features.

## Production Notes

- Production Web Push requires HTTPS.
- Browser Web Push coexists with the existing in-app toast notifications; it does not replace them.
- Service-worker updates follow the browser's normal update lifecycle.
- Different browsers may vary in how aggressively they surface background notifications or persist permission prompts.

## Production deployment

Every push to `master` runs dependency installation, lint, type checking, unit tests, and a production build. Only after those checks pass does it deploy the same commit to the production server's `production` branch through `.github/workflows/deploy-production.yml`.

Before the first deployment, add these GitHub Actions repository secrets:

- `PRODUCTION_DEPLOY_SSH_KEY`: the private SSH key authorized for `transpo-24-admin@88.99.63.223`.
- `PRODUCTION_KNOWN_HOSTS`: the exact `known_hosts` entry for `88.99.63.223` (generate it from a trusted machine with `ssh-keyscan -H 88.99.63.223`).

The server's existing receive hook is responsible for checking out, building, and restarting the production app after the push arrives.

## Commands

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

The browser regression suite uses a local mock API and starts its own Next.js development server on ports 3215 and 3216. With `playwright-core` available in `NODE_PATH` and Chrome installed, run `npm run test:browser`. It does not call the real backend.

Docker uses Node 22 and the pnpm lockfile. Pass the `NEXT_PUBLIC_*` values listed above as Docker build arguments; Next.js embeds public configuration at build time. Local environment files are excluded from the Docker context.
